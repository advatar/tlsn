# CR-004: Browser Demo EAS Integration Plan

## Goal

Bring this repo's browser demo close to the public onchain demo by adding:

- session metadata that survives the proof lifecycle
- verifier-driven webhook delivery after successful verification
- an optional EAS relay service that can mint Sepolia attestations from verified outputs

The target is to reuse the useful upstream ideas without trying to pull the full `tlsn-extension` application model into this Rust workspace.

## What Upstream Actually Adds

There are two separate upstream inputs:

1. `tlsnotary/tlsn` has an `interactive-with-eas` branch with a Rust `eas` example. It is useful as a reference for EAS contract details and local attestation flow, but it is not merged on `upstream/main` and it rides on a much larger refactor branch.
2. The live public demo flow lives in `tlsnotary/tlsn-extension`. That repo contains the wallet registration flow, verifier webhook routing, Spotify plugin, and `eas-webhook` service that the public demo site uses today.

For this repo, the reusable design is the extension repo's `correlationId + webhook + relay` pattern, not a direct merge of the `interactive-with-eas` branch.

## Scope Freeze

The first implementation should stay tight:

1. Add a generic webhook and attestation pipeline to `crates/browser-demo`, not full extension/plugin parity.
2. Keep one chain target: Ethereum Sepolia.
3. Keep one relay mode: a single attester key and one schema at a time.
4. Carry opaque `session_data` through the proof flow, with `correlation_id` as the required key for EAS mode.
5. Derive attestation payload fields from verified output on the server side; do not trust browser-supplied attestation fields.
6. Treat Spotify-specific UX as a later phase. The current browser demo does not have the extension's OAuth/token interception model, so exact public-demo parity is not the first milestone.

## Current Repo Fit

The existing browser demo already gives us most of the transport pieces:

- `crates/browser-demo/src/lib.rs` exposes `/ws/notary/{session_id}`, `/ws/tcp`, and `/api/sessions/{session_id}`.
- `crates/browser-demo/static/app.js` already creates the proof session, computes reveal ranges via WASM, and polls verifier output.
- `crates/sdk-core/src/handler/mod.rs` already translates handler configs into reveal ranges, which is the right place to extend result extraction.
- `crates/attestation/src/signing.rs` already includes Ethereum-compatible secp256k1 signature support, so low-level key handling is not the blocker.

The gap is application plumbing: session metadata, verified result extraction, webhook dispatch, and an EAS relay.

## Recommended Architecture

### 1. Session Metadata and Lifecycle

Add an explicit session-creation step before the WebSocket proof starts.

Recommended shape:

- Add `POST /api/sessions` to allocate a `session_id` and persist session metadata.
- Keep `GET /api/sessions/{session_id}` for polling.
- Keep `GET /ws/notary/{session_id}` and load the saved session record when verification completes.

Recommended session metadata:

- `session_data: BTreeMap<String, String>`
- `handlers: Vec<Handler>`
- `webhook_mode: none | local | remote`
- `attestation_mode: none | eas`

Recommended server-side model changes:

- replace the current `SessionStore<HashMap<String, SessionSnapshot>>` with a `SessionRecord`
- keep `status`, `output`, and `error`
- add `metadata`
- add `webhook_status`
- add `attestation_status`

This keeps the browser demo architecture intact instead of building a second orchestration path next to it.

### 2. Structured Verified Results

The current handler pipeline only returns byte ranges for reveal. That is not enough for webhook consumers like the upstream EAS relay, which expect structured values such as a revealed JSON field.

Recommended change:

- extend `crates/sdk-core/src/handler/mod.rs` to return extracted values as well as ranges
- surface the richer output through `crates/wasm/src/handler.rs`
- persist the handler config in the session record
- on verifier completion, materialize structured results from the verified partial transcript and stored handlers

Target webhook result shape:

```json
{
  "server_name": "api.spotify.com",
  "results": [
    {
      "type": "RECV",
      "part": "BODY",
      "value": "Radiohead"
    }
  ],
  "session": {
    "correlationId": "uuid"
  }
}
```

Important rule:

- the server must only emit values that were actually authenticated and disclosed in the verified transcript

If the current `ComputeRevealOutput` API is too browser-oriented to do that cleanly, add a second server-side helper dedicated to materializing verified handler results from a `PartialTranscript`.

### 3. Webhook Dispatch

Add optional post-verification webhook delivery to the browser demo server.

Recommended config changes:

- extend `AppConfig` in `crates/browser-demo/src/main.rs`
- allow a small per-host webhook mapping, similar in spirit to the extension repo's `verifier-config.yaml`
- keep the config local to the browser demo server instead of introducing a full extension-style config loader

Recommended behavior:

- send webhooks only after verifier status is `Complete`
- include `server_name`, `connection_info`, structured `results`, `session_data`, and either:
  - a transcript hash only, or
  - a full extension-compatible transcript object behind an explicit opt-in
- mark webhook outcome in the session record
- keep delivery asynchronous so the proof flow is not blocked on relay latency

Recommended first payload choice:

- compute `transcript_hash = keccak256(sent || recv)` on the browser demo server
- send the hash to remote webhook consumers by default
- avoid sending full raw transcript content unless the operator explicitly enables it

That default keeps the generic browser demo closer to least-privilege behavior than the public demo wiring.

### 4. EAS Relay Service

The fastest route is to adapt the upstream Node service rather than reimplement it in Rust immediately.

Recommendation:

- import the upstream `tlsn-extension/packages/eas-webhook` service into this repo as a small demo helper
- keep it outside the Rust workspace, under a top-level helper directory such as `tools/eas-webhook/`
- preserve its current environment contract:
  - `PRIVATE_KEY`
  - `EAS_SCHEMA_UID`
  - `SEPOLIA_RPC`
  - `VERIFIER_URL`

Why this is the right v0:

- it matches the live demo's semantics
- it minimizes drift from the upstream public flow
- it avoids spending phase-one time on Rust Ethereum client selection and contract call plumbing

Deferred follow-up:

- after the webhook payload and front-end flow stabilize, decide whether a Rust port is worth the maintenance cost

### 5. Browser Demo UI

The current UI in `crates/browser-demo/static/app.js` needs a second path beyond "request then reveal":

1. Connect wallet.
2. Sign a registration message.
3. Register `correlation_id -> wallet address` with the relay.
4. Start the proof session with matching `session_data`.
5. Finalize reveal as today.
6. Poll attestation status and show `tx_hash` and `attestation_uid`.

Recommended v0 UX:

- generic "attest revealed value" mode first
- wallet section stays hidden unless EAS mode is enabled
- if EAS mode is off, the browser demo behaves exactly as it does today

Recommended attested field shape for v0:

- `revealedValue: string`
- `fieldLabel: string`
- `serverName: string`
- `verifierUrl: string`
- `transcriptHash: bytes32`
- `timestamp: uint64`

This is a better fit for the current generic browser demo than a Spotify-only schema.

## Delivery Phases

### Phase 1: Session Contract and Mock Webhooks

Scope:

- add `POST /api/sessions`
- persist metadata with the session record
- add webhook configuration to the browser demo server
- dispatch a mock webhook after successful verification

Files likely touched:

- `crates/browser-demo/src/lib.rs`
- `crates/browser-demo/src/main.rs`
- `crates/browser-demo/static/app.js`
- `crates/browser-demo/README.md`

Definition of done:

- a proof session can carry `session_data`
- the session poll API shows webhook state
- a local mock receiver gets a verified payload after session completion

### Phase 2: Verified Result Materialization

Scope:

- extend handler output beyond reveal ranges
- materialize verified values on the server
- include structured results in webhook payloads

Files likely touched:

- `crates/sdk-core/src/handler/mod.rs`
- `crates/sdk-core/src/handler/extract.rs`
- `crates/sdk-core/src/handler/tests.rs`
- `crates/wasm/src/handler.rs`
- `crates/wasm/src/types.rs`
- `crates/browser-demo/src/lib.rs`

Definition of done:

- a JSON-path handler can produce both a reveal plan and a verified value
- webhook payloads contain structured result values
- tests cover both range extraction and value extraction

### Phase 3: EAS Relay Integration

Scope:

- import or adapt the upstream `eas-webhook` helper
- wire browser-demo webhook config to that service
- add docs and local run wrappers

Files likely touched:

- `tools/eas-webhook/*`
- `scripts/browser-demo.sh`
- `package.json`
- `crates/browser-demo/README.md`

Definition of done:

- a completed proof can create a Sepolia attestation through the relay
- the UI can show pending, complete, and error states from the relay

### Phase 4: UX Presets and Spotify Follow-up

Scope:

- add a preconfigured "generic JSON field" attestation mode
- evaluate whether a Spotify-specific mode is viable without extension-only auth capture

Definition of done:

- the generic mode is polished enough for demos
- Spotify-specific work is either implemented with a credible auth path or explicitly deferred

Focused checks per phase:

- `cargo test -p tlsn-browser-demo`
- `cargo test -p tlsn-sdk-core handler`
- `cargo check -p tlsn-wasm`

Additional test coverage to add:

- verified handler-value extraction from JSON bodies and headers

For Sepolia itself:

- keep real chain submission as an opt-in manual verification path
- do not make public RPC availability or funded wallets a required CI dependency

## Risks and Decisions

### Decision: Keep v0 Generic

The public Spotify demo depends on extension behavior this repo does not have. The first milestone should prove the webhook/EAS pattern with the existing browser demo rather than chase a UI parity target that is blocked on OAuth capture.

### Decision: Prefer Upstream Relay Reuse

The EAS relay should initially stay close to the upstream `tlsn-extension` service. Re-implementing it in Rust too early creates avoidable drift.

### Risk: Privacy Drift

If the browser demo starts forwarding raw transcript content to webhooks by default, it will exceed what is necessary for EAS attestations. Default to hashed transcript linkage and structured verified fields.

### Risk: Browser Trust Boundary Confusion

The browser may compute reveal plans, but the server must remain the source of truth for any value that gets forwarded to a webhook or anchored onchain.

## Recommended First PR Sequence

1. Session creation API and session metadata storage in `tlsn-browser-demo`.
2. Mock webhook dispatch and session status extensions.
3. Structured verified handler results in `tlsn-sdk-core` and `tlsn-wasm`.
4. Import and document the EAS relay helper.
5. Wallet and attestation UI in the browser demo.

That sequence gives us useful intermediate milestones and keeps the browser demo operable at every step.
